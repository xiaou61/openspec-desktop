## Why

当前应用已经能够分别计算 OpenSpec 工件状态和任务门槛，但生命周期轨道仍把 `tasks` 工件的 `done` 直接显示为“任务已完成”。因此，一个曾经达到 100% 后又新增待办或重新打开任务的 Change，会同时出现“57/64、仍有 7 项任务”和任务节点对勾，用户也无法看出它已经进入新一轮实施。

与此同时，应用给出了单个 Change 的建议下一步，却没有把跨项目待办、OpenSpec 健康状态和可交给 Codex 执行的动作集中起来。实际使用时，用户仍需逐项进入 Change、判断这是首次开发还是再次实施，并手工拼接后续操作上下文。

## What Changes

- 增加应用级 OpenSpec 行动中心，跨所有已登记项目按当前证据汇总需要补充工件、继续实施、重新严格验证、检查归档或处理环境问题的 Change，并支持聚焦当前项目以及从行动项回到具体 Change 和证据。
- 行动中心优先消费 OpenSpec CLI 的 `status`、`instructions`、`doctor` 和 `context` 结构化结果，展示实际 schema、工件依赖、阻塞和根目录健康；CLI 不可用时明确降级，不把结构推测伪装成权威结论。
- 为可执行行动生成带项目根、Change 身份和动作类型的 Codex 交接内容，支持复制或打开对应工作上下文；应用本身继续保持 OpenSpec 项目文件只读，不自动生成工件、修改任务或执行归档。
- 修正生命周期任务节点语义：`tasks` 工件为 `done` 只表示任务清单已经创建并满足工件依赖，不再等同于实施任务全部完成。任务节点必须同时结合 task gate；存在未勾选任务时显示当前实施状态、完成数和剩余数，不得显示完成对勾。
- 增加 Change 实施轮次状态。当应用已经观察到一个包含至少一项任务的 Change 达到全完成，随后又因新增未完成任务或取消既有勾选而回到未完成时，将其标记为“再次实施”并进入下一轮；在 Change 列表、详情标题和活动记录中展示轮次、重新打开时间、任务变化和当时版本上下文。
- 实施轮次证据保存在应用本地数据中并跨重启保留，不写入项目目录。首次监控时已经未完成、从未被应用确认完成、仅有 `0/0` 任务或只有格式变化的 Change，不得被猜测为二次开发。
- 区分“同一 Change 再次实施”和“已归档能力继续演进”：前者来自同一 Change 的完成到未完成转换；后者由新 Change 对既有主规格能力产生增量时标记为“能力迭代”，不修改旧 Change 的完成与归档事实。
- 已归档 Change 的源文件若再次发生修改，应用显示异常提示并建议创建新的 Change，不把直接修改归档内容计为新的实施轮次。
- 将界面中的“严格验证”和“可归档”继续限定为 OpenSpec 文档校验与归档就绪，不将任务勾选、交接动作或二次开发标记表述为代码交付已经通过验证。

## Capabilities

### New Capabilities

- `openspec-action-center`: 汇总所有已登记项目的 OpenSpec 下一步、环境健康、阻塞证据和面向 Codex 的安全行动交接。
- `change-implementation-iterations`: 区分任务工件就绪与实施完成，识别同一 Change 完成后重新打开的实施轮次，并区分后续能力演进与归档内容异常修改。

### Modified Capabilities

无。仓库当前尚未把对应能力归档到 `openspec/specs/`，本变更以独立新增能力描述后续行为，避免把另一个未归档 Change 的 delta 当作主规格修改。

## Impact

- 共享契约与生命周期领域模型需要表达任务工件状态、task gate、实施轮次、重新打开原因和行动项来源，避免把多个独立事实压成一个完成状态。
- 文件监控与本地历史需要在稳定投影之间识别“完成 -> 未完成”转换，并以可迁移、可裁剪但不会因普通修订保留策略而丢失的方式保存轮次里程碑。
- OpenSpec CLI 适配层将增加受限的 `instructions`、`doctor` 和 `context` 只读调用，并继续使用无 shell、参数白名单、超时和输出上限。
- IPC、preload 和 React 工作区将增加行动中心查询、Codex 交接、实施轮次徽标、任务节点复合状态和语义化活动记录。
- 需要覆盖新增待办、取消勾选、首次扫描、重启恢复、历史裁剪、版本切换、CLI 缺失、自定义 artifact、已归档文件变化以及 `57/57 -> 57/64` 等回归场景。
