## Purpose

使 OpenSpec Change 在任务清单完成后再次出现未完成工作时得到准确、持久且可解释的“再次实施”标记，同时避免把工件存在、能力演进或归档内容修改误报为新的实施轮次。

## ADDED Requirements

### Requirement: 任务节点必须区分任务工件就绪与实施任务完成

系统 MUST 将 `tasks` 工件已存在或被 OpenSpec 标记为 `done` 解释为任务清单和工件依赖已就绪，而不是实施任务已经完成。对于需要 tasks 的 Change，生命周期任务节点 MUST 同时使用可读取任务清单的完成数、总数和剩余数决定实施状态；仅当总数大于零且全部任务已勾选时，节点才可显示实施完成对勾。任务清单不可读、缺失、总数为零或仍有未勾选任务时，节点 MUST 使用相应的未知、待实施或任务清单已就绪状态，且 MUST NOT 显示实施完成对勾。

#### Scenario: 已创建任务清单但仍有剩余任务

- **WHEN** OpenSpec 将 `tasks` 工件报告为 `done`，且任务清单为已完成 57 项、总计 64 项
- **THEN** 生命周期任务节点 MUST 显示当前实施状态、57/64 和剩余 7 项任务
- **THEN** 节点 MUST NOT 显示“已完成”文字或完成对勾

#### Scenario: 已完成的非空任务清单

- **WHEN** 一个需要 tasks 的 Change 具有至少一项任务，且每一项均已勾选
- **THEN** 生命周期任务节点 MUST 显示实施任务已完成
- **THEN** 严格验证和归档就绪 MUST 继续作为独立结论展示

#### Scenario: 空任务清单

- **WHEN** 一个需要 tasks 的 Change 的任务总数为零
- **THEN** 系统 MUST 显示任务清单已就绪或无可追踪任务
- **THEN** 该状态 MUST NOT 创建实施完成里程碑或再次实施标记

### Requirement: 系统必须以持久的完成到未完成转换识别再次实施

系统 MUST 仅在同一未归档 Change 的稳定观察记录表明其曾具有总数大于零且全部完成的任务门槛，随后变为存在未完成任务时，创建新的实施轮次。首次观察到未完成任务、从未被应用确认全完成、只有零任务、仅 Markdown 格式变化或无法可靠解析任务时，系统 MUST NOT 推断再次实施。首次被应用确认全完成的非空任务清单建立第 1 轮完成里程碑；后续满足转换条件时，系统 MUST 将当前工作标记为“再次实施”及第 N 轮，其中 N 至少为 2。

#### Scenario: 新增未完成任务重新打开 Change

- **WHEN** 系统已经稳定确认同一当前 Change 的 57/57 非空任务全部完成，随后稳定扫描到 57/64
- **THEN** 系统 MUST 创建第 2 轮实施并标记为“再次实施”
- **THEN** 系统 MUST 记录重新打开时间、此前和当前任务计数、任务变化以及当时项目版本上下文

#### Scenario: 取消既有完成勾选重新打开 Change

- **WHEN** 系统已经稳定确认一个当前 Change 的非空任务全部完成，随后同一任务清单出现未勾选任务而总数不增加
- **THEN** 系统 MUST 创建新的实施轮次并将重新打开原因标记为任务重新打开或等价的可解释原因
- **THEN** 系统 MUST NOT 将该事件仅显示为普通任务进度变化

#### Scenario: 应用首次见到未完成 Change

- **WHEN** 应用首次扫描一个已完成 57 项、总计 64 项的 Change，且没有本地全完成里程碑
- **THEN** 系统 MUST 显示该 Change 正在实施并显示任务计数
- **THEN** 系统 MUST NOT 标记“再次实施”或猜测其此前完成过

### Requirement: 实施轮次证据必须保存在独立的本地持久状态中

系统 MUST 将实施轮次的完成里程碑、当前轮次、重新打开证据和版本上下文保存于应用本地数据，并在同一已登记项目重启后恢复。常规修订和活动历史的保留或裁剪 MUST NOT 删除仍用于判断再次实施的轮次里程碑。轮次状态损坏、缺失或无法迁移时，系统 MUST 以不标记再次实施的保守状态恢复，并提供明确的本地数据不可用提示；系统 MUST NOT 将轮次证据写入 OpenSpec 项目文件。

#### Scenario: 重启后发现新增任务

- **WHEN** 应用在重启前已保存一个 Change 的非空任务全完成里程碑，重启后扫描到该 Change 存在未完成任务
- **THEN** 系统 MUST 继续识别该 Change 为再次实施
- **THEN** 行动、列表、详情和活动记录 MUST 使用恢复后的同一轮次信息

#### Scenario: 常规历史裁剪

- **WHEN** 本地历史因其常规保留策略删除了旧修订或普通活动
- **THEN** 与仍存在 Change 对应的实施轮次里程碑 MUST 继续可用于再次实施判断
- **THEN** 系统 MUST NOT 因缺少旧任务快照而重新猜测或丢失已确认的轮次

### Requirement: 再次实施信息必须在 Change 工作流中一致呈现

系统 MUST 在 Change 列表、Change 详情标题、行动中心和活动记录中一致显示已识别的再次实施状态。显示内容 MUST 至少包含当前轮次、重新打开时间、可用的重新打开原因和任务变化；活动记录 MUST 保留触发该轮次时的项目版本上下文。标签 MUST 描述 OpenSpec 任务重新进入实施，MUST NOT 宣称代码交付、严格验证或归档已经完成。

#### Scenario: 用户查看再次实施 Change

- **WHEN** 用户打开已被标记为第 2 轮实施的 Change
- **THEN** 列表和详情标题 MUST 显示“再次实施”及第 2 轮信息
- **THEN** 用户 MUST 能从活动记录查看触发轮次的任务变化、时间和版本上下文

#### Scenario: 用户在版本上下文中查看活动

- **WHEN** 用户查看一个再次实施事件的活动记录
- **THEN** 该活动 MUST 显示事件发生时关联的项目版本标签或明确的无版本上下文状态
- **THEN** 版本筛选或切换 MUST NOT 将事件误显示为其他版本产生的轮次

### Requirement: 系统必须区分再次实施、能力迭代和归档内容异常

系统 MUST 仅把同一当前 Change 的已确认完成到未完成转换标记为“再次实施”。当一个新的当前 Change 对已存在于主规格中的能力产生 delta 时，系统 MUST 将其标记为“能力迭代”，并保持任何旧 Change 的完成轮次和归档事实不变。已归档 Change 在被应用稳定观察后其源文件又发生变化时，系统 MUST 显示归档内容异常，建议创建新的 Change，并且 MUST NOT 把该修改计入实施轮次或自动改回当前 Change。

#### Scenario: 新 Change 演进已归档能力

- **WHEN** 一个新的当前 Change 的 delta specs 指向已存在于主规格的能力
- **THEN** 系统 MUST 将该 Change 标记为能力迭代
- **THEN** 系统 MUST NOT 将旧 Change 显示为再次实施或改变其归档状态

#### Scenario: 已归档 Change 被直接修改

- **WHEN** 系统已稳定观察一个已归档 Change，随后其归档目录内允许监控的源文件发生内容变化
- **THEN** 系统 MUST 显示归档内容异常和创建新 Change 的建议
- **THEN** 系统 MUST NOT 自动还原文件、移动 Change、创建实施轮次或把归档 Change 视为当前实施
