## Purpose

让桌面应用能够把 Codex 索引中的容器目录识别为多项目工作区，安全发现其中真正的 OpenSpec 项目，并在不混淆项目边界的前提下完成选择、导入和持久分组。

## ADDED Requirements

### Requirement: 区分直接项目与多项目工作区

系统 SHALL 先按精确根路径判断 Codex 索引项是 OpenSpec 项目、可读取的容器目录还是不可用路径；只有不包含直接 OpenSpec 结构的可读取目录才进入工作区成员发现。

#### Scenario: 根路径本身是 OpenSpec 项目

- **WHEN** Codex 索引根路径包含可识别且可读取的 `openspec/` 结构
- **THEN** 系统将该根路径显示为直接项目候选，并且不扫描其后代目录寻找嵌套项目

#### Scenario: 根路径包含多个独立代码仓库

- **WHEN** Codex 索引根路径本身没有 `openspec/`，但其后代中存在一个或多个可识别的代码仓库或 OpenSpec 项目
- **THEN** 系统将该根路径显示为工作区，而不是标记为“不是 OpenSpec 项目”

#### Scenario: 多仓库演示工作区

- **WHEN** 一个容器目录包含三个独立代码仓库，其中一个仓库已配置 OpenSpec，另外两个尚未配置
- **THEN** 系统显示“包含 3 个代码仓库，其中 1 个 OpenSpec 项目”，并将已配置仓库标记为可导入

#### Scenario: 根路径不可读取

- **WHEN** Codex 索引根路径不存在或不可读取
- **THEN** 系统保留该索引项并显示可恢复的不可用原因，不尝试扫描其后代目录

#### Scenario: 未发现项目结构

- **WHEN** 可读取根路径既不是直接 OpenSpec 项目，也未在发现边界内找到代码仓库或 OpenSpec 项目
- **THEN** 系统显示“未发现 OpenSpec 项目或代码仓库”，且该项不可选择

### Requirement: 有界且安全地发现工作区成员

系统 MUST 对工作区发现设置固定的最大深度、目录检查数量、成员数量、并发度和时间预算；系统 MUST 跳过依赖、版本控制和构建输出目录，不得跟随符号链接或目录联接，并在找到有效 OpenSpec 根后停止扫描其后代。

#### Scenario: 扫描普通容器目录

- **WHEN** 工作区在限制范围内包含若干代码项目
- **THEN** 系统仅通过目录结构和受支持的项目标记识别成员，不读取源代码、对话内容或凭据

#### Scenario: 遇到高成本目录

- **WHEN** 工作区包含 `node_modules`、`.git`、`dist`、`build`、`target` 或其他配置的排除目录
- **THEN** 系统不进入这些目录，也不将其内容计入项目成员

#### Scenario: 遇到符号链接或目录联接

- **WHEN** 扫描路径包含指向工作区内部或外部的符号链接或目录联接
- **THEN** 系统不跟随该路径，并继续处理其他可读取成员

#### Scenario: 找到有效 OpenSpec 根

- **WHEN** 扫描到一个有效 OpenSpec 项目根目录
- **THEN** 系统将其作为单个项目成员，并且不继续扫描该项目根目录的后代

#### Scenario: 达到扫描预算

- **WHEN** 任一深度、目录、成员或时间预算被耗尽
- **THEN** 系统停止调度新的目录读取，保留已经发现的结果，并明确标记结果已截断及其原因

#### Scenario: 单个成员不可读取

- **WHEN** 工作区中的一个候选成员在扫描期间变为不可读取
- **THEN** 系统记录该成员或工作区的局部诊断，并继续返回其他已发现成员

### Requirement: 分类工作区成员及其 OpenSpec 状态

系统 SHALL 区分有效 OpenSpec 项目、尚未配置 OpenSpec 的代码仓库和无法识别的普通目录；只有有效且尚未注册的 OpenSpec 项目才具有导入资格。

#### Scenario: 代码仓库已配置 OpenSpec

- **WHEN** 工作区成员具有可识别且可读取的 OpenSpec 结构
- **THEN** 系统将其显示为“OpenSpec 项目”，并根据是否已注册决定可选择状态

#### Scenario: 代码仓库未配置 OpenSpec

- **WHEN** 工作区成员具有受支持的代码仓库或项目标记，但没有有效 OpenSpec 结构
- **THEN** 系统将其显示为“尚未配置 OpenSpec”，说明不可导入原因，并且不提供自动初始化副作用

#### Scenario: 普通资料目录

- **WHEN** 工作区中的目录不具有 OpenSpec、版本库或受支持的项目标记
- **THEN** 系统不把该目录计入代码仓库或可导入项目数量，也不将其误报为无效项目

#### Scenario: 子项目已经注册

- **WHEN** 发现的 OpenSpec 子项目与目录中现有项目的规范化路径相同
- **THEN** 系统将其标记为“已添加”并禁止重复导入

### Requirement: 在重叠来源中稳定去重

系统 SHALL 以平台规范化后的真实绝对路径作为项目和工作区身份，在直接 Codex 索引项、已保存工作区和嵌套发现结果之间合并重复路径，并为每个项目只返回一个可导入身份。

#### Scenario: 子项目同时被 Codex 直接索引

- **WHEN** 同一 OpenSpec 根路径既是 Codex 直接索引项，又从父工作区中被发现
- **THEN** 系统只显示一个项目身份，并保留其工作区归属和 Codex 排序信息

#### Scenario: 多个容器覆盖同一子项目

- **WHEN** 两个重叠工作区都发现同一个子项目
- **THEN** 系统使用最近的祖先工作区作为归属，并在距离相同时使用 Codex 索引顺序确定结果

#### Scenario: Windows 路径表示不同

- **WHEN** 大小写、尾部分隔符或扩展路径前缀不同的路径指向同一目录
- **THEN** 系统将其合并为同一个项目或工作区身份

### Requirement: 分层呈现工作区和准确计数

系统 SHALL 在 Codex 导入界面中以可展开的工作区行包含项目成员行，并分别统计 Codex 根目录、工作区、代码仓库、OpenSpec 项目和当前可导入项目，所有状态 MUST 同时使用文字表达。

#### Scenario: 展示包含可导入项目的工作区

- **WHEN** 工作区包含一个或多个有效 OpenSpec 子项目
- **THEN** 父行显示工作区标识和成员摘要，展开后显示每个成员的名称、路径、类型和导入状态

#### Scenario: 统计可导入数量

- **WHEN** 一个工作区包含可导入、已添加和未配置 OpenSpec 的不同成员
- **THEN** 顶部“可导入”数量只计算有效且尚未注册的 OpenSpec 子项目

#### Scenario: 展示截断或局部诊断

- **WHEN** 工作区发现被截断或部分目录读取失败
- **THEN** 导入界面在对应工作区和总体摘要中显示非阻塞提示，同时保留已确认安全的候选

#### Scenario: 键盘展开工作区

- **WHEN** 键盘用户聚焦工作区展开控件并触发该控件
- **THEN** 系统展开或折叠成员列表、更新可访问展开状态，且不改变当前选择

### Requirement: 工作区选择只作用于可导入子项目

系统 SHALL 为工作区提供全选其可导入子项目的父级复选框，并根据子项目选择状态呈现未选、部分选择和全部选择；父目录、已添加项目和未配置 OpenSpec 的仓库 MUST NOT 进入导入请求。

#### Scenario: 选择工作区

- **WHEN** 用户选中一个包含多个可导入子项目的工作区复选框
- **THEN** 系统选中该工作区内所有可导入子项目，并准确更新总选择数量

#### Scenario: 取消部分子项目

- **WHEN** 用户在已全选的工作区中取消一个可导入子项目
- **THEN** 父复选框显示部分选择，其他子项目保持选中

#### Scenario: 工作区没有可导入成员

- **WHEN** 工作区只包含已添加项目或尚未配置 OpenSpec 的代码仓库
- **THEN** 父复选框不可用，且界面说明当前没有可导入项目

#### Scenario: 折叠后确认导入

- **WHEN** 用户选择子项目后折叠工作区并确认导入
- **THEN** 系统保留选择，并仅提交已选择子项目的规范化项目根路径和工作区来源信息

### Requirement: 独立导入并持久关联工作区

系统 SHALL 在确认时重新校验每个选中的子项目，将其逐个注册为独立 OpenSpec 项目，并在首个子项目成功后创建或复用以规范化来源根路径标识的工作区分组；一个子项目失败 MUST NOT 回滚其他成功项目。

#### Scenario: 从工作区导入一个子项目

- **WHEN** 用户从工作区选择一个有效 OpenSpec 子项目并确认
- **THEN** 系统注册子项目根路径、启动现有扫描与监控，并把项目关联到对应工作区分组，而不注册父目录

#### Scenario: 再次从同一工作区导入

- **WHEN** 用户稍后从同一规范化工作区根路径导入另一个子项目
- **THEN** 系统复用已有自动工作区分组，不创建同名重复分组

#### Scenario: 工作区名称与手工分组相同

- **WHEN** 已存在同名手工分组但其身份不具有相同工作区来源根路径
- **THEN** 系统不按名称错误复用该手工分组，并保持手工分组成员不变

#### Scenario: 导入期间部分失效

- **WHEN** 多选导入期间某个子项目被删除、失去 OpenSpec 结构或移出声明的工作区根路径
- **THEN** 系统拒绝该子项目、保留其他成功导入结果，并返回逐项中文失败原因

#### Scenario: 已添加项目属于其他分组

- **WHEN** 发现的子项目已经注册且属于其他手工或自动分组
- **THEN** 系统不重复注册，也不自动改变其现有分组归属

### Requirement: 保持项目级 OpenSpec 边界和目录兼容性

系统 MUST 将工作区作为本地组织元数据而非 OpenSpec 项目；每个导入子项目 SHALL 独立计算 Change、任务、规格、版本、历史和归档状态，现有直接导入项目与手工分组行为 MUST 保持兼容。

#### Scenario: 工作区包含多个 OpenSpec 项目

- **WHEN** 用户在主侧边栏展开一个自动工作区分组
- **THEN** 系统显示其已导入子项目，选择其中一个项目时只展示该项目自己的 OpenSpec 投影

#### Scenario: 子项目执行归档

- **WHEN** 工作区中的一个子项目归档 Change
- **THEN** 系统只更新该子项目的长期规格和状态，不修改父目录或其他子项目

#### Scenario: 导入未配置的代码仓库

- **WHEN** 用户查看尚未配置 OpenSpec 的工作区成员
- **THEN** 系统不创建 `openspec/`、不生成规格，也不启动项目监控

#### Scenario: 读取现有目录数据

- **WHEN** 应用升级后加载已有项目和手工分组
- **THEN** 系统迁移目录元数据并保持现有分组名称、顺序、成员关系和项目选择不变

#### Scenario: 移除自动工作区分组

- **WHEN** 用户移除自动工作区分组
- **THEN** 系统仅解除其项目分组关系，已注册项目、历史记录和监控状态保持不变

#### Scenario: 直接项目导入保持不变

- **WHEN** Codex 根路径本身是有效 OpenSpec 项目
- **THEN** 系统继续允许按原有扁平项目流程选择和导入，不强制创建工作区分组

#### Scenario: 不提供跨项目 Change

- **WHEN** 工作区包含多个已导入 OpenSpec 项目
- **THEN** 系统不把它们的 Change、任务或规格合并成一个父级 Change
