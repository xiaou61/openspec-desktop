## Context

见 `proposal.md`。当前 `main` 与 `origin/main` 都指向 `5f8d07b`，但工作区包含多轮已完成且尚未提交的产品实现、测试和 OpenSpec 规划文件，也包含 `.tmp-wmi-diagnosis/` 与 `output/` 等生成内容。GitHub 远端已经存在、当前为公开仓库且本机认证可用，因此本 Change 的难点不是创建仓库，而是建立可复核的发布边界，并让手册准确对应最终待发布版本。

## Goals / Non-Goals

**Goals:**

- 通过显式文件清单和验证门槛，把当前可用源码安全推送到既有公开 `main`。
- 产出一份首次使用者可独立跟随、与最终界面一致、可在 GitHub 直接阅读的中文操作手册。
- 让 README 成为稳定入口，而不是重复维护完整手册。
- 保留发布前后的可追溯证据：待提交清单、验证结果、提交 SHA 和远端核对结果。

**Non-Goals:**

- 不创建新仓库，不改变仓库可见性、默认分支或权限。
- 不创建分支/worktree，不 force push，也不重写现有历史。
- 不发布 npm 包、GitHub Release、版本标签、安装器或便携包。
- 不新增运行时功能、帮助菜单、文档站点生成器或 CI/CD。
- 不顺带归档、同步或改写其他已完成 Change；相关规划文件是否纳入源码提交只按当前产品实现的可追溯性判断。

## Decisions

### 1. 使用“允许清单”暂存，而不是 `git add -A`

实现者先按功能组审阅 `git status --short`、`git diff --stat`、未跟踪目录和 `.gitignore`，再显式暂存确认属于当前产品的源码、测试、文档与 OpenSpec 记录。`.tmp-wmi-diagnosis/`、`output/` 以及验证中新生成的报告不得进入索引；对稳定可再生的根目录补充根路径 `.gitignore` 规则。

选择该方式是因为当前工作区不是单一小改动，盲目全量暂存会把诊断输出、本机路径或无关产物公开。替代方案是先清空或重置工作区再逐项恢复，但它会破坏用户现有改动，因此不可采用。

### 2. 手册使用仓库原生 Markdown 与同仓库相对图片

主文档固定为 `docs/user-manual.md`，截图放在 `docs/assets/user-manual/`，文档使用相对链接，确保本地 Markdown 预览与 GitHub 渲染都可用。README 仅提供简短快速开始、完整手册入口和开发者信息。

选择 Markdown 是因为它无需引入文档构建链，源码与说明可在同一提交中审阅。Word/PDF 会产生额外的版本同步和渲染维护成本，本次不做。

### 3. 手册围绕用户任务组织，不围绕代码模块组织

章节顺序固定为：适用范围与前置条件、获取/安装/启动、首次接入项目、识别单项目和多项目工作区、浏览 Change、理解状态与生命周期、执行任务与再次实施、运行严格验证、处理失败、归档及长期规格影响、查看历史/活动、设置与本地数据、备份/迁移/卸载、常见故障。

每个关键操作写清入口、前置条件、操作步骤、成功结果和失败处理；术语首次出现时解释，但不复制 OpenSpec 官方规范全文。手册只描述最终版本真实存在的控件和行为，所有命令、按钮名、状态名均需从运行中的应用与当前 CLI 实测核对。

### 4. 截图来自最终构建，并使用脱敏演示数据

在文档文字稳定后启动最终待发布版本，以测试夹具或不含个人目录名的演示项目拍摄少量关键截图。至少覆盖工作区总览、Change 详情/生命周期、就地严格验证、任务再次实施或历史查看；只有截图能明显减少歧义时才加入。

截图使用统一窗口尺寸，避免裁掉关键控件；不得出现访问令牌、用户账号、真实私有项目名或绝对本机路径。替代方案是仅写文字，但该产品以可视化操作为核心，纯文字不足以帮助首次使用者定位入口。

### 5. 发布验证分为“内容验证”和“远端验证”

推送前依次完成：检查差异与换行/空白、文档链接和图片存在性、敏感信息/大文件审计、`pnpm typecheck`、`pnpm lint`、`pnpm test`、`pnpm check:renderer-boundary`、`pnpm build`、与本次用户流程相关的 Playwright/Electron E2E，以及 `openspec validate publish-source-and-add-user-manual --strict --no-interactive`。若某项因环境原因未运行，不能伪装为通过，须在交付记录中说明。

推送前执行 fetch 并确认 `main` 未落后或分叉；若远端已变化则停止并处理冲突，禁止 force push。推送后通过 GitHub API/CLI 核对远端 HEAD、README 手册链接及截图资源，最终交付必须报告提交 SHA 和仓库 URL。

### 6. 提交按可审阅的逻辑边界组织

现有未提交产品实现与本次文档/仓库卫生改动可形成一个或少量逻辑提交，但每个提交都必须能从暂存差异解释，不强制压成单提交，也不混入生成产物。提交信息使用仓库现有 Conventional Commits 风格。发布动作在所有验证完成后进行，不能用“先推再修”替代本地验收。

## Risks / Trade-offs

- [当前工作区跨度大，漏审或误收文件] → 逐组审阅并显式暂存，提交前再次对比 `git diff --cached --stat` 与 `git status --short`。
- [公开仓库泄露本机信息或秘密] → 对已跟踪和拟暂存内容进行凭据模式、绝对路径和大文件检查，截图只使用脱敏演示数据。
- [手册与最终 UI 不一致] → 文案从最终构建实测，截图在文字和功能稳定后采集，关键流程由另一遍手工跟随验证。
- [README 与手册重复后发生漂移] → README 只保留入口级说明，操作细节只在用户手册维护。
- [直接推送 `main` 缺少 PR 审核缓冲] → 这是用户明确采用的串行工作方式；以严格的本地差异审计、完整验证和禁止 force push 降低风险。
- [没有 Release/安装包使非开发者无法直接下载使用] → 本次目标是源码公开和操作说明；二进制分发需要版本、签名、升级与回滚决策，后续单独规划。

## Migration Plan

1. 记录当前远端、HEAD 和完整工作区状态，建立拟发布允许清单与明确排除清单。
2. 完成仓库卫生规则、用户手册、截图和 README 导航，逐项核对真实应用行为。
3. 运行本地验证并修复仅由本次整理暴露的问题，不借机扩大产品范围。
4. 显式暂存允许清单，复核缓存差异、敏感信息、大文件和生成产物后创建逻辑提交。
5. fetch 并确认远端没有新提交，正常 push 到 `origin/main`，随后核对 GitHub 页面和资源。
6. 若推送前失败，保留本地提交并修复后重验；若推送后发现文档错误，以新的修复提交前进，不改写公开历史。
