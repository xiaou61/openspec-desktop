## Why（为什么）

当前工作区主要用任务勾选比例表达进度，无法区分“任务已完成”“严格验证已通过”“delta specs 将在归档时如何更新主规格”和“已经归档”等不同事实。多个任务 100% 的 Change 仍会出现在“进行中”，用户需要逐个打开文件或调用 OpenSpec 才能判断下一步，进度展示因此不够准确，也容易让 AI 把完成与归档混为一谈。

## What Changes（变更内容）

- 为每个 Change 建立可解释的生命周期就绪模型，分别展示工件完整度、任务进度、严格验证和归档状态，不再用一个百分比代替全部状态；规格影响作为归档详情保留，不作为独立阶段。
- 在 Change 详情顶部增加可点击的生命周期轨道，按 proposal、specs、design、tasks、验证和归档顺序展示当前节点、已完成节点与阻塞节点。
- 根据 OpenSpec 工件依赖、未完成任务和严格验证结果生成唯一的“建议下一步”及具体阻塞原因；本地 delta 对比只提供归档影响预览，不覆盖 OpenSpec CLI 的权威验证结论，也不单独阻塞归档。
- 提供只读的严格验证入口与最近验证结果，安全调用本机 OpenSpec CLI；CLI 不可用时保持其他监控能力并给出可操作说明。
- 在归档详情中对 delta specs 与主规格进行只读影响预览，按能力汇总 ADDED、MODIFIED、REMOVED 和 RENAMED 变化，区分“无需更新”“归档时将更新”“已反映”和“预览不可用”。
- 增加归档就绪检查：工件完成、任务完成且严格验证通过时显示“可以归档”；规格影响预览不可用时提供警告但不制造额外流程。归档仍必须由用户明确确认，本应用不会自动移动 Change。
- 将现有“进行中 / 归档”导航语义调整为“当前变更 / 已归档”，并在当前变更内部继续区分实施中、已完成、待验证和可归档，避免目录状态与任务状态混淆。
- Change 列表在“当前变更”和“已归档”范围内分别按最近活动时间倒序排列，时间相同使用 Change ID 稳定排序；每页显示 10 条，仅在超过一页时显示分页，并在切换项目或范围时回到第一页。
- 保持项目源文件只读；生命周期结论必须标明数据来源与检查时间，不执行 spec 同步、归档、任务勾选或其他项目写入。

## Capabilities（能力范围）

### New Capabilities（新增能力）

- `change-lifecycle-readiness`：定义 Change 多维生命周期、可视化轨道、下一步建议、严格验证、归档影响预览、归档就绪判断以及 Change 列表的时间排序与分页。

### Modified Capabilities（修改能力）

无。当前主规格目录尚未归档对应能力，本变更以新增能力描述行为。

## Impact（影响范围）

- 主进程：增加 OpenSpec 状态读取、受限严格验证、delta/main spec 对比和就绪评估服务；所有项目命令继续使用无 shell、有超时与输出上限的调用方式。
- 共享契约与 IPC：增加生命周期节点、检查来源、验证结果、同步摘要、阻塞原因和建议下一步的严格 schema 与只读接口。
- 渲染进程：调整 Change 导航命名和详情信息架构，增加生命周期轨道、下一步区域与归档影响预览，并为 Change 列表增加稳定倒序和分页控件。
- 本地状态：保存验证结果与检查时间等可丢弃缓存，不把派生状态或工具输出写入项目目录。
- 隐私与兼容：不上传项目路径、文档或命令输出；未安装 OpenSpec CLI、旧 Change 格式和解析异常均有明确降级状态。
- 测试：覆盖生命周期组合、CLI 缺失/超时、验证失败、归档影响差异、预览不可用不阻塞、时间倒序、分页边界、键盘导航和实时文件变化后的状态失效。
